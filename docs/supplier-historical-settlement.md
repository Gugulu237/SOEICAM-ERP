# Clear paid setup bills

An administrator with Purchases and Accounting access can open a supplier's **Bills** tab and choose **Clear paid setup bills**. This exceptional correction is only for abandoned setup entries that falsely show debt for purchases already paid before the official accounting start. It must not be used to settle genuine unpaid bills or hide operational transactions.

Select all outstanding bills for the supplier, the official accounting start date, the prior-payment/setup reference and an active migration equity clearing account. Review each original receipt journal, credit account and amount, then explicitly confirm that these were abandoned setup bills already paid before the start and no supplier debt remains.

The operation archives the bills with a cancelled status, a zero balance and an **Archived setup bill** label. It leaves `amount_paid` unchanged at zero because no ERP payment occurred. The existing receiving journal keeps its number, date, amounts and inventory debit. Only the erroneous supplier payable credit is reassigned to the selected equity clearing account, with its supplier party removed. The complete opening trial balance must reconcile this clearing account. This changes the classification of an original setup entry; it does not post a new settlement journal, backdate a payment, or classify the correction as current income or expense.

An immutable server audit stores the complete original bill, receipt, purchase order, journal header, journal lines, supplier and affected accounts, together with the administrator, timestamp, reference, start date and resulting account changes. Receipts and orders are marked to prevent another bill or payment. Stock, receiving quantities, sales, customer balances, rent and other suppliers remain unchanged. No journal or journal line is created or deleted; no Payment, PaymentAllocation, TreasuryTransaction, expense or StockMovement is created.

Bills, receipts and their original journals must all predate the chosen start date. The order must be fully received. Recorded or pending supplier payments, partial payments, missing or conflicting source evidence, unmatched supplier debt, inconsistent account caches, closed source/current periods, duplicate receiving journals and stale previews block the operation. The date is a cutoff for this correction, not a global accounting-date reset. The API requires the new setup-cleanup mode so a previously cached settlement form cannot apply this different operation.

The correction is atomic and one-time per supplier. A durable audit identifier, preview fingerprint and transaction lock protect retries. Repeating an identical confirmation returns the saved result; a different confirmation after completion is rejected. A failure rolls back all original-entry changes, archived bills, account caches and audit together.

Deploying or building this feature never changes company records. An administrator must apply it explicitly after deployment. Run `node --test tests/supplier-historical-settlement.test.mjs tests/supplier-historical-settlement-ui.test.mjs` for isolated regression coverage.
